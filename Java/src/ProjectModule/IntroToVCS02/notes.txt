# Problems without VCS -
• Multiple people are going to work on the same codebase at the same time.
• Conflict might happen when multiple developers are writing code on the same line.
• How to manage code history?
• We might want to check the exact history of the codebase

# VCS
• Allows us to maintain the complete history of the codebase by storing all the versions.
• Each version contains meaningful amount of code changes on top of the previous version

# Types of VCS -
• Centralized VCS
- Complete codebase is present on a centralized server
- We need to be connected to the internet in order to make code changes
- Example - Google Docs, Spreadsheets

• Pros -
- Security
- Simple & Secure
- Space Efficient

• Cons -
- SPOF (Single Point Of Failure)
- We need to be connected to the internet to make the code changes

• Distributed VCS ->
- User downloads the codebase from the central server to their local machine (Cloning)
- Users can make changes in the codebase in their local m/c without connecting to central server
- Once user is done with the code changes, they can submit the code changes to the central sever

• Pros -
- No need to stay connected with the central server
- No SPOF

• Cons -
- Merge conflict might occur
- Ambiguity

# GIT is the most popular distributed VCS using which we can maintain the complete history of the codebase
and multiple developers can work together.
• Was created by Linus Torvalds, also created Linux OS.

# Git Vs GitHub
Git -> Software to manage the versions of the codebase
GitHub -> Place to host git enable repos

# Git Commit
- Every commit will have author, title, description, delta, id(globally unique id).
- Every commit is immutable.
- Once a commit has been made we cannot edit any attribute of it.
- We don't edit the same commit but a new commit is created.

# Commit ID - hash(author, title, desc, timestamp, m/c info, List<PrevCommit> prevCommits)
- Every commit just contains the delta over the previous commit
